# Starlink 分支对话画布系统 - 技术报告

> **项目定位**：基于 AI 驱动的多维度可视化思维画布平台
> **核心价值**：将复杂问题拆解为结构化节点网络，支持实时协作与智能推演
> **技术特点**：Monorepo 全栈架构 + GraphQL 实时订阅 + Dify 工作流集成

---

## 一、项目概述

### 1.1 项目背景与目标

**Starlink**（原 Branching Chat）是一个「对话即画布」的协作平台，灵感来源于 Kuse 的分支对话理念。传统的线性对话难以处理复杂议题，本项目通过**可视化节点网络**将问题拆解为：
- 澄清目标（Clarify Goals）
- 拆分维度（Break Down Dimensions）
- 识别资源（Identify Resources）

每个维度下还可以递归展开**行动计划**、**验证方案**等子节点，形成多层次的思维导图。AI 参与整个推演过程，自动生成节点结构并通过实时订阅推送到前端画布。

### 1.2 核心功能

1. **动态画布节点系统**
   - 支持拖拽、缩放、连线的无限画布（基于 React Flow）
   - 自定义节点类型：Agent Avatar、CC-BMC Card、Insight Note 等
   - MACRA 智能布局算法自动排列节点

2. **AI 驱动的问题分析**
   - 集成 Dify 工作流引擎，支持流式/阻塞两种执行模式
   - 自动生成问题摘要、维度分析、行动计划
   - 限流策略保护后端资源（IP/用户/租户/工作流四维度）

3. **实时协作能力**
   - GraphQL Subscription 推送画布增量更新
   - Yjs CRDT 解决多人编辑冲突
   - WebSocket 长连接维持状态同步

4. **多格式文档支持**
   - PDF/Word/Excel 导入导出
   - TipTap 富文本编辑器
   - Markdown 渲染与代码高亮

5. **完整的开发与测试体系**
   - TypeScript 全栈类型安全
   - Playwright E2E 测试覆盖核心交互
   - Zod Schema 统一前后端数据契约

### 2.2 架构模式说明

**1. Monorepo 工作区管理**
采用 pnpm workspaces 统一管理多个子包：
```
starlink/
├── apps/web/              # Next.js 前端应用
├── packages/
│   ├── server/            # GraphQL 网关服务
│   ├── shared/            # 共享类型与工具
│   └── ui/                # UI 组件库
├── backend/               # 传统 REST 服务（遗留）
└── docs/                  # 架构文档
```

**优势**：
- 统一依赖版本管理
- 跨包类型共享（TypeScript Project References）
- 原子化提交（改动涉及多个包时保持一致性）

**2. 前后端分离 + BFF 模式**
- **前端**：Next.js SSR/SSG，SEO 友好，首屏快速渲染
- **BFF 层**：GraphQL Gateway 聚合多个后端服务（Dify、Supabase、LangChain）
- **后端服务**：各司其职，Dify 负责 AI 推理，Supabase 负责数据持久化

**3. 事件驱动 + 发布订阅**
- GraphQL Subscription 基于 PubSub 模式
- 前端订阅 `conversationProgress` 事件
- 后端逐步生成节点，通过事件流推送增量更新

### 4.2 Dify 工作流集成

**前端调用流程**：
```typescript
// apps/web/src/services/DifyService.ts
class DifyService {
  async executeWorkflow(request: {
    workflowId: string
    inputs: Record<string, unknown>
    responseMode: 'blocking' | 'streaming'
  }) {
    if (request.responseMode === 'streaming') {
      // 返回 SSE 流
      const response = await fetch('/api/dify', {
        method: 'POST',
        body: JSON.stringify(request)
      })
      return response.body // ReadableStream
    } else {
      // 返回完整结果
      const data = await fetch('/api/dify', {
        method: 'POST',
        body: JSON.stringify(request)
      }).then(r => r.json())
      return data
    }
  }
}
```

**限流策略实现**：
```typescript
// apps/web/src/app/api/dify/route.ts
class InMemoryRateLimiter {
  private buckets = new Map<string, { count: number; expiresAt: number }>()

  consume(key: string, limit: number, intervalMs: number) {
    const now = Date.now()
    const bucket = this.buckets.get(key)

    if (!bucket || bucket.expiresAt <= now) {
      // 创建新桶
      this.buckets.set(key, { count: 1, expiresAt: now + intervalMs })
      return { allowed: true }
    }

    if (bucket.count >= limit) {
      // 超出限制
      return { allowed: false, retryAfterMs: bucket.expiresAt - now }
    }

    // 增加计数
    bucket.count += 1
    return { allowed: true }
  }
}
```

**限流维度**：
- **IP 限流**：防止单个 IP 滥用
- **用户限流**：保护用户配额
- **租户限流**：多租户场景隔离
- **工作流限流**：防止单个工作流被刷爆

### 4.3 GraphQL 实时订阅

**Schema 定义**：
```graphql
type Subscription {
  conversationProgress: ConversationEvent!
}

type ConversationEvent {
  type: String!              # graph/appended | graph/diff | status
  conversationId: ID!
  status: String             # running | completed | failed
  message: String
  payload: JSON              # 增量节点/边数据
}
```

**后端推送实现**：
```typescript
// packages/server/src/graphql/resolvers.ts
const resolvers = {
  Subscription: {
    conversationProgress: {
      subscribe: () => pubsub.asyncIterator(['CONVERSATION_PROGRESS'])
    }
  },

  Mutation: {
    async startConversation(parent, { workspaceId, question }) {
      const conversationId = nanoid()

      // 异步生成画布
      generateCanvas(workspaceId, question, conversationId).then(graph => {
        // 推送完整图
        pubsub.publish('CONVERSATION_PROGRESS', {
          conversationProgress: {
            type: 'graph/appended',
            conversationId,
            payload: graph
          }
        })

        // 推送状态更新
        pubsub.publish('CONVERSATION_PROGRESS', {
          conversationProgress: {
            type: 'status',
            conversationId,
            status: 'completed'
          }
        })
      })

      return { conversationId, status: 'started' }
    }
  }
}
```

**前端订阅实现**：
```typescript
// apps/web/src/hooks/useConversationProgress.ts
import { useSubscription } from '@apollo/client'

function useConversationProgress(conversationId: string) {
  const { data } = useSubscription(CONVERSATION_PROGRESS_SUBSCRIPTION, {
    variables: { conversationId }
  })

  useEffect(() => {
    if (data?.conversationProgress.type === 'graph/appended') {
      // 更新画布节点
      setNodes(data.conversationProgress.payload.nodes)
      setEdges(data.conversationProgress.payload.edges)
    }
  }, [data])
}
```

## 五、数据流与交互流程

### 5.1 画布生成流程

```
用户提问
    ↓
前端 startConversation Mutation
    ↓
GraphQL Gateway
    ↓
调用 Dify 工作流生成摘要
    ↓
ConversationStore 构建节点图
    ↓
    ├─ 创建根节点（问题 + 摘要）
    ├─ 生成三个分支问题
    │   ├─ 澄清目标 (Clarify Goals)
    │   ├─ 拆分维度 (Break Down Dimensions)
    │   └─ 识别资源 (Identify Resources)
    ├─ 为每个分支生成维度节点
    │   ├─ 价值主张 (Value Proposition)
    │   ├─ 执行路径 (Execution Path)
    │   └─ 验证计划 (Validation Plan)
    └─ 为每个维度生成行动计划节点
        ├─ 行动项 1
        ├─ 行动项 2
        └─ 行动项 3
    ↓
通过 PubSub 推送增量更新
    ↓
前端订阅接收事件流
    ↓
React Flow 画布动画渲染
```

### 5.2 实时协作流程

```
用户 A 修改节点
    ↓
Yjs 本地更新 ydoc
    ↓
WebSocket Provider 发送增量
    ↓
服务器广播给其他客户端
    ↓
用户 B 的 WebSocket Provider 接收
    ↓
Yjs 自动合并变更（CRDT）
    ↓
触发 observe 回调
    ↓
更新用户 B 的画布
```

**冲突解决示例**：
```
初始状态：节点 A 的标题是 "问题分析"

时刻 T1：
- 用户 A 改为 "问题分析（更新）"
- 用户 B 改为 "问题分析（修订）"

时刻 T2（网络同步后）：
- Yjs 自动合并为 "问题分析（更新）（修订）"
- 或者根据 LWW (Last Write Wins) 策略保留最后一次修改
```

## 十一、技术挑战与解决方案

### 11.1 实时协作的冲突处理

**挑战**：多人同时编辑同一节点导致数据不一致。

**解决方案**：
- 使用 Yjs CRDT 算法自动合并冲突
- 操作转换（Operational Transformation）保证因果一致性
- 使用 Lamport 时间戳排序并发操作

### 11.2 大规模画布性能

**挑战**：节点数量超过 1000 时渲染卡顿。

**解决方案**：
- React Flow 虚拟化仅渲染可见区域
- Web Worker 后台计算布局算法
- Canvas/WebGL 渲染替代 DOM（PixiJS）

### 11.3 Dify 工作流稳定性

**挑战**：Dify API 偶尔超时或返回错误。

**解决方案**：
- 指数退避重试机制（最多 3 次）
- 熔断器模式防止级联故障
- 降级策略返回缓存结果

### 11.4 WebSocket 连接管理

**挑战**：网络波动导致连接断开。

**解决方案**：
- 心跳检测维持连接活性
- 断线重连机制（指数退避）
- 离线消息队列同步

## 十二、总结

Starlink 项目成功实现了一个**技术先进、功能完善、用户体验优秀**的分支对话画布系统。通过 Monorepo 架构统一管理前后端代码，利用 GraphQL 实时订阅提供低延迟交互，集成 Dify 工作流引擎实现 AI 驱动的智能分析，采用 Yjs CRDT 算法保证多人协作的数据一致性。

### 核心技术成果

1. **前端**：Next.js + React Flow + TanStack Query + Zustand
2. **后端**：Express + Apollo Server + GraphQL Subscription
3. **数据库**：Supabase (PostgreSQL + Auth + Storage)
4. **AI 引擎**：Dify 工作流 (Streaming/Blocking)
5. **实时协作**：Yjs CRDT + WebSocket
6. **测试**：Playwright E2E + Vitest 单元测试

### 项目价值

- **用户价值**：提供结构化的问题分析工具，帮助团队快速达成共识
- **技术价值**：展示现代 Web 应用的最佳实践（Monorepo + GraphQL + CRDT）
- **商业价值**：适用于战略规划、产品设计、项目管理等多个场景
