## 摘要

基于大语言模型（LLM）的多智能体系统，已经在自动化问题求解方面取得了明显进展。现有方法已经能够完成一些较简单的对话类任务，但一旦任务变得更复杂，直接把多个 LLM 串联起来，往往会因为级联式幻觉而出现逻辑不一致，进而影响最终结果。为了解决这一问题，本文提出了 MetaGPT。它是一种新的元编程框架，旨在把高效的人类工作流程引入基于 LLM 的多智能体协作中。

MetaGPT 将标准操作流程（Standardized Operating Procedures, SOP）编码为一组提示序列，从而形成更清晰、更规范的工作流。借助这种方式，具备类似人类领域专长的智能体可以检查中间结果、减少错误。MetaGPT 还采用“装配线”式协作模式，为不同智能体分配不同角色，把复杂任务拆解为多个子任务，再由多个智能体协同完成。

在协作式软件工程基准上，MetaGPT 相比此前基于对话的多智能体系统，能够生成更连贯的解决方案。项目地址为：<https://github.com/geekan/MetaGPT>。

## 1 引言

利用大语言模型构建自治智能体，为提升和复现人类工作流程带来了新的可能。不过，在真实应用场景中，现有系统往往把问题简化得过于理想化。尤其是在需要有效协作的复杂任务里，它们通常难以形成连贯、准确且真正可执行的问题求解过程。

在人类长期的协作实践中，各个领域已经逐渐形成了被广泛接受的标准操作流程（SOP）。SOP 对任务拆解和高效协作非常关键。它不仅明确了不同成员的职责，也为中间产出设定了统一标准。清晰的 SOP 可以提高任务执行的一致性和准确性，使各项工作更好地符合既定角色和质量要求。以软件公司为例，产品经理通常会按照标准化结构分析竞品和用户需求，形成产品需求文档（PRD），以此指导后续开发。

受此启发，本文设计了一个基于 GPT 的元编程框架 MetaGPT，并将 SOP 深度融入其中。与已有工作不同，MetaGPT 要求智能体生成结构化输出，例如需求文档、设计产物、流程图和接口规范。引入这些中间结构化产物后，目标代码的生成成功率明显提高，因为这种方式有助于保持协作过程中的沟通一致性，减少歧义和错误。

更直观地说，在 MetaGPT 模拟的“软件公司”中，所有成员都遵循严格且精简的工作流程，所有交接都必须符合既定标准。这样可以降低 LLM 因无效闲聊而产生幻觉的风险，尤其是在角色扮演式框架中，例如：

> “Hi, hello and how are you?” - Alice（产品经理）  
> “Great! Have you had lunch?” - Bob（架构师）

得益于 SOP，MetaGPT 为元编程提供了一条很有潜力的思路。这里所说的元编程，是指“用程序来编程”，它不同于更宽泛的元学习，后者更强调“学习如何学习”。

这一元编程思路也覆盖了更早的代码模型工作，例如 CodeBERT，以及后来的 CodeLlama、WizardCoder 等项目。但 MetaGPT 的特别之处在于，它通过一个组织良好、分工明确的专门化智能体团队来高效完成元编程任务。每个智能体都有明确角色和专业能力，并遵循既定标准。因此，系统可以在运行时自动完成需求分析、系统设计、代码生成、修改、执行和调试，体现出基于智能体的技术如何增强元编程能力。

为了验证 MetaGPT 的设计，本文在公开基准 HumanEval 和 MBPP 上进行了评估。值得注意的是，在代码生成任务上，MetaGPT 在 Pass@1 指标上分别取得了 85.9% 和 87.7% 的新 SOTA。与 AutoGPT、LangChain、AgentVerse 和 ChatDev 等复杂软件生成框架相比，MetaGPT 在更高层级的软件复杂度和功能完整性方面表现更强。在实验中，MetaGPT 甚至达到了 100% 的任务完成率，显示出该设计在鲁棒性和效率（时间与 token 成本）上的优势。

本文的主要贡献如下：

1. 提出 MetaGPT，这是一种面向 LLM 多智能体协作的元编程框架。它具有较高的便利性与灵活性，并提供角色定义、消息共享等明确功能，可作为开发 LLM 多智能体系统的实用平台。
2. 在 MetaGPT 的整体设计中创新性地融入了类人 SOP，从而显著提升系统鲁棒性，减少基于 LLM 的智能体之间低效、无产出的协作。同时，本文还引入了一种新的可执行反馈机制，在运行时执行与调试代码，从而明显提升代码生成质量，例如在 MBPP 上带来 5.4% 的绝对提升。
3. 在 HumanEval 与 MBPP 上取得 SOTA 表现。大量实验结果有力验证了 MetaGPT 的有效性，说明它是一个很有前景的基于 LLM 多智能体系统开发的元编程框架。

## 2 相关工作

### 2.1 自动编程

自动编程的概念可以追溯到上世纪。1969 年，Waldinger 和 Lee 提出了 PROW 系统，尝试根据用谓词演算写成的程序规格自动生成算法，并给出 LISP 实现。Balzer 和 Soloway 随后继续推进这一方向，提出了实现自动编程的若干思路。近年来，相关研究更多借助自然语言处理技术。自动编程也逐渐从研究问题发展为产业能力，例如 Microsoft Copilot 这类实际产品。

近来，基于 LLM 的智能体进一步推进了自动编程的发展。其中，ReAct 与 Reflexion 通过思维链提示，让 LLM 生成推理轨迹和行动计划。这些工作都证明了“推理-行动循环”作为一种设计范式在自动编程中的有效性。此外，ToolFormer 还展示了语言模型如何通过简单 API 学会使用外部工具。

与本文最接近的工作包括：Li 等提出的基于角色扮演的编程框架，以及 Qian 等将多智能体用于软件开发的工作。尽管这些方法提高了生产效率，但它们尚未充分利用带有结构化输出格式的有效工作流，因此在面对复杂软件工程问题时仍然存在不足。

### 2.2 基于 LLM 的多智能体框架

近年来，基于 LLM 的自治智能体在工业界和学术界都引起了广泛关注。许多工作通过引入多智能体讨论来提升大语言模型的问题求解能力。Stable-Alignment 通过 sandbox 中多个 LLM 智能体的交互，在价值判断上形成共识，从而构造指令数据集。还有一些工作更关注社会学现象，例如 Generative Agents 构建了一个由 25 个智能体组成的小镇，用于研究语言交互、社会理解和集体记忆；NLSOM 则让具有不同功能的智能体通过多轮“头脑风暴”来解决复杂任务。

另一些工作关注计划、协作与竞争，还有一些尝试构建基于 LLM 的经济系统。这些研究大多聚焦于开放世界中的人类行为模拟，而 MetaGPT 更强调把人类在真实协作中的经验明确引入多智能体框架。除此之外，基于 LLM 的智能体还普遍面临“重复指令”或“消息无限循环”等问题。在面向任务的协作中，这类问题会更加明显，因为这类协作要求互动既一致又有效。这也是本文将软件开发中的标准操作流程引入多智能体框架的主要动机。

## 3 MetaGPT：一种元编程框架

MetaGPT 是一个面向基于 LLM 的多智能体系统的元编程框架。第 3.1 节介绍框架中的角色专门化、工作流程和结构化协作方式，并说明如何在 SOP 的语境下组织多智能体系统。第 3.2 节提出一种能够提高角色间通信效率的协议，并实现结构化通信接口以及高效的发布-订阅机制，使智能体能够从其他角色和环境中获取有针对性的信息。第 3.3 节则进一步引入可执行反馈机制，用于在运行过程中提升代码生成质量。

### 3.1 标准操作流程中的智能体

#### 角色专门化

清晰明确的角色专门化可以将复杂工作拆解成更小、更具体的任务。解决复杂任务或问题，往往需要多个具备不同技能和专长的智能体协同合作，每个智能体针对特定问题提供专门化输出。

在软件公司中，产品经理通常负责偏业务的分析与需求提炼，软件工程师则负责程序实现。本文在模拟的软件公司中定义了五种角色：产品经理、架构师、项目经理、工程师和测试工程师，如图 1 所示。在 MetaGPT 中，每个角色都有对应的 profile，包括姓名、角色描述、目标和约束，并初始化相应的上下文和技能。例如，产品经理可以使用网络搜索工具，而工程师可以执行代码，如图 2 所示。所有智能体都遵循 Yao 等（2022）提出的 ReAct 风格行为。每个智能体都会持续监控环境，也就是 MetaGPT 中的消息池，以捕捉重要观察结果，例如来自其他角色的消息。这些消息既可以直接触发动作，也可以帮助完成当前任务。

#### 智能体之间的工作流

通过定义智能体的角色与操作技能，我们可以建立基本工作流。本文遵循软件开发中的 SOP，使所有智能体可以按照顺序协作完成工作。

具体而言，如图 1 所示，在接收到用户需求后，产品经理首先进行全面分析，形成详细的 PRD，其中包括用户故事与需求池，从而完成初步的功能拆解。随后，这份结构化 PRD 被交给架构师，后者将需求转化为系统设计组件，例如文件清单、数据结构和接口定义。系统设计完成后，相关信息再交给项目经理进行任务分配。工程师则依据图 2 右侧所示的迭代式编程与反馈流程，完成指定类与函数的实现。随后，测试工程师生成测试用例，以保证代码质量。最终，MetaGPT 产出一个较为完整的软件解决方案。论文中还给出了更详细的 SOP 工作流示意图以及一个具体实例，具体见附录 B。

### 3.2 通信协议

#### 结构化通信接口

当前大多数基于 LLM 的多智能体框架，都把自然语言作为开放式通信接口。不过，自然语言虽然灵活，也会带来一个问题：如果完全依赖自然语言通信，是否足以处理复杂任务？例如，在“传话游戏”中，信息经过多轮传递后，原始内容往往会被严重扭曲。

受人类社会结构启发，本文提出用结构化通信来规范智能体之间的交流。我们为每个角色设定 schema 和格式，并要求角色根据自身职责与上下文给出必要输出。

如图 3 所示，架构师智能体会生成两个关键产物：系统接口设计与顺序流程图。这些文档包含系统模块设计和交互顺序，是工程师执行工作的关键依据。与 ChatDev 不同，MetaGPT 中的智能体是通过文档和图表等结构化产物进行沟通，而不是通过自然语言对话。这样生成的文档包含完成工作所需的必要信息，可以避免无关或缺失内容。

#### 发布-订阅机制

在协作中，共享信息至关重要。例如，架构师和工程师经常需要参考 PRD。如果每次都采用一对一方式传递这类信息，通信拓扑会变得复杂，效率也会下降。

为解决这一问题，本文提出将信息存放在一个全局消息池中。如图 2 左图所示，我们引入共享消息池，使所有智能体能够直接交换消息。智能体既可以将结构化消息发布到池中，也可以透明地访问其他实体发布的信息。这样一来，任何智能体都可以直接从共享池中取回所需信息，而无需逐一询问其他角色并等待回应，从而提高通信效率。

当然，如果把所有信息都发给所有智能体，也会导致信息过载。在任务执行过程中，某个智能体通常只希望接收与自身任务相关的信息，而不希望被无关信息干扰。因此，信息的有效管理与分发同样重要。

本文提供了一种简单而有效的订阅机制。智能体不依赖对话，而是根据角色特定的兴趣点来筛选相关信息。它们可以依据自身角色画像选择关注哪些信息。在具体实现中，一个智能体只有在收到完成当前动作所需的全部前置依赖后，才会真正触发行动。例如，如图 3 所示，架构师主要关注产品经理提供的 PRD，而像测试工程师等角色生成的文档对架构师来说就没有那么重要。

### 3.3 带可执行反馈的迭代式编程

在日常编程任务中，调试和优化都非常重要。但现有方法往往缺少有效的自我纠错机制，因此经常会出现代码生成失败的问题。已有工作虽然引入了不可执行的代码审查和自我反思机制，但这些方法仍然很难真正保证代码可以运行，并且在运行时保持正确。

在 MetaGPT 的早期实现中，由于 LLM 幻觉，我们发现审查过程会忽略某些错误。为解决这一问题，在初始代码生成之后，本文引入了一种可执行反馈机制，以迭代方式改进代码。

更具体地说，如图 2 所示，工程师首先根据原始产品需求和设计文档编写代码。随后，工程师会利用自身历史执行与调试记忆持续改进代码。为了获取更多信息，工程师还会编写并执行相应的单元测试，并接收测试结果。如果测试通过，则进入下一步开发任务；如果没有通过，则先调试代码再继续编程。该迭代测试过程会一直持续，直到测试通过，或达到最多 3 次重试上限。

## 4 实验

### 4.1 实验设置

#### 数据集

本文使用了两个公开基准：HumanEval 和 MBPP，以及一个自建的、更具挑战性的软工开发基准 SoftwareDev。

1. **HumanEval**：包含 164 个手写编程任务。这些任务包含函数规格说明、任务描述、参考代码和测试。
2. **MBPP**：包含 427 个 Python 任务，覆盖核心概念与标准库特性，并提供描述、参考代码和自动化测试。
3. **SoftwareDev**：由 70 个具有代表性的软件开发任务组成，每个任务都有自己的任务提示词。任务范围多样，例如小游戏、图像处理算法、数据可视化等，更适合作为真实开发任务的测试平台。与 HumanEval 和 MBPP 不同，SoftwareDev 更关注工程实现层面的能力。

在对比实验中，作者随机选取了其中 7 个代表性任务进行评估。

#### 评估指标

对于 HumanEval 和 MBPP，本文采用无偏版本的 Pass@k 来评估前 k 个生成代码的功能正确性。

对于 SoftwareDev，作者更加关注实际可用性，并通过人工评估与统计分析两类方式进行评价：

- **可执行性（Executability）**：从 1 到 4 打分，1 表示失败或不可运行，2 表示可运行但不完善，3 表示基本符合预期，4 表示完全无误。
- **成本（Cost）**：包括运行时间、token 使用量和费用。
- **代码统计（Code Statistics）**：包括代码文件数量、每个文件的代码行数以及总代码行数。
- **生产率（Productivity）**：定义为 token 使用量除以总代码行数，表示生成一行代码平均消耗多少 token。
- **人工修正成本（Human Revision Cost）**：指人工修改代码的次数，主要用于修复包导入错误、类名错误、引用路径不完整等问题。通常每次修正不超过 3 行代码。

#### 基线方法

作者将 MetaGPT 与代码生成领域的若干专用 LLM 进行比较，包括 AlphaCode、Incoder、CodeGeeX、CodeGen、Codex、CodeT，以及通用大模型 PaLM 和 GPT-4。对于 SoftwareDev，作者还将其与 AutoGPT、带 Python REPL 工具的 LangChain、AgentVerse 和 ChatDev 进行了系统性比较。

## 附录 A 展望

### A.1 自我改进机制

正文中使用的 MetaGPT 版本存在一个限制：每个软件项目都是彼此独立执行的。但在真实团队协作中，软件开发团队理应能够从每个项目中积累经验，并随着时间推移变得更默契、更高效。

这一点与递归式自我改进的思想存在一定联系。相关思想最早在 1965 年被非正式提出，1987 年以后出现了更具体的实现，最终发展到数学上最优的自指型自我改进系统。一般而言，一个系统应当能够从现实世界经验中学习，并从“学习的经验”中元学习出更好的学习算法，再从“元学习的经验”中学习出更好的元学习算法，以此递归推进，除了可计算性和物理规律以外不受其他限制。

一些更近的相关工作利用大语言模型的推理能力，通过递归地改进提示词来提升下游任务表现。这与 2015 年提出的“自适应提示工程师”思想相似：一个神经网络学会为另一个预训练网络生成查询或提示序列，而后者给出的回答又能帮助前者更快学会新任务。

在本文工作中，作者也探索了一种自指机制：根据智能体在软件开发过程中观察到的信息，递归地修改其约束性提示词。其初始实现方式如下：在每个新项目开始前，软件公司中的每个智能体都会回顾以往反馈，并对其约束性提示进行必要调整。这样，每个个体都能持续从过去项目经验中学习，进而提升整个多智能体系统。作者首先为每个智能体建立了一种“交接反馈动作”，负责总结该智能体在先前项目中收到的信息，并将其融入更新后的约束提示。总结信息会被存入长期记忆，以便后续项目继续继承和使用。新项目启动时，每个智能体首先执行 react 动作，评估收到的反馈，并总结自身应如何改进。

目前的一个限制在于，这种基于总结的优化只会修改角色专门化中的约束，而不会修改通信协议中的结构化通信接口。未来还需要进一步探索。

### A.2 多智能体经济

在真实团队协作中，交互流程往往不是硬编码不变的。例如，在软件公司里，协作 SOP 可能会根据情况动态调整。

这类自组织的一种实现方式，体现在 “Natural Language-Based Society of Mind” 一文中提出的 “Economy of Minds” 思想。它是一个面向 LLM 与其他智能体社会的强化学习框架。不同于标准强化学习通过修改神经网络参数来最大化系统总奖励，EOM 利用自由市场中的供需原则，把“信用”或“金钱”分配给那些真正促进经济成功（即奖励）的智能体。

DeepWisdom 最近推出的智能体平台 AgentStore 与这种信用分配理念是兼容的。在 AgentStore 中，每个智能体都会提供一组带有相应成本的服务，并开放便捷的 API，使人类用户或平台中的其他智能体能够直接购买这些服务来完成任务。图 6 展示了 AgentStore 的界面，其中列出了各种具备不同技能的智能体。除此之外，个人开发者也可以参与构建新的智能体，从而在社区中形成协同开发。

具体来说，AgentStore 允许用户按需订阅智能体，并根据使用量付费。用户还可以购买额外能力，以扩展已有智能体的即插即用功能，使智能体逐步升级。在 MetaGPT 框架中，AgentStore 可以支持多种智能体之间的协作。用户可以将多个智能体组合起来完成更复杂的任务或项目，并让所有智能体共享并遵守 MetaGPT 规定的开发与通信协议。

from tkinter import colorchooser

class ColorPicker:
    def __init__(self, root: tk.Tk, color: str = 'black'):
        self.frame = tk.Frame(root)
        self.color = color

        self.color_button = tk.Button(self.frame, text='Color', command=self.select_color)

    def select_color(self):
        color = colorchooser.askcolor()[1]
        if color is not None:

## 附录 D 局限性与伦理问题

### D.1 局限性

#### 系统侧

目前，MetaGPT 还无法完全适配某些特定场景，例如 UI 和前端开发，因为系统尚未纳入相应角色与多模态工具。除此之外，尽管 MetaGPT 相比同类框架能生成更多代码，但面对真实世界应用的多样与复杂需求时，仍然存在明显挑战。

#### 用户侧

对用户来说，一个关键问题是如何在每个智能体运行时进行中断，或者为每个智能体设定启动检查点（checkpoint）。

### D.2 伦理问题

#### 失业与技能过时

MetaGPT 让更多人能够通过自然语言进行编程，从而降低了编程的入门门槛。多年来，编程语言已经从穿孔卡片发展到汇编、C、Java、Python，再到今天的自然语言。结果并不是程序员需求减少，反而是人类编程能力不断增强，并带来了更多与编程相关的岗位。自然语言编程的学习门槛更低，因此也可能让更多人掌握编程能力。

#### 透明性与责任归属

MetaGPT 是一个开源框架，支持多个智能体通过自然语言进行交互式通信。人类可以在最高控制级别下发起、观察并中止运行。系统会在屏幕和日志中实时展示自然语言的解释与执行过程，从而保证透明性。MetaGPT 增强的是“自然语言编程”能力，而最终的使用者和结果责任主体仍然是人类工程师。

#### 隐私与数据安全

MetaGPT 在本地运行，从而保证用户数据隐私和安全，不会主动收集用户数据。对于与第三方 LLM（例如 OpenAI）交互的情况，用户应参考相应平台的隐私政策。同时，系统也提供开源 LLM 作为后端选项。

## 附录 E 更多讨论

### E.1 深层挑战

MetaGPT 通过其独特设计，在一定程度上缓解了以下几个更深层次的问题：

#### 更高效地利用上下文

这里包含两个子挑战。第一，如何准确展开简短的自然语言描述、消除歧义；第二，如何在长上下文中保持信息有效性，使 LLM 能专注于相关数据而不被干扰。

#### 减少幻觉

使用 LLM 直接生成完整软件程序会面临代码幻觉问题，包括函数实现不完整、依赖缺失以及难以发现的潜在 bug，而这类问题在软件生成中往往更严重。LLM 之所以在软件生成上容易出错，一个重要原因是任务定义过于模糊。与其让模型直接处理宽泛任务，不如把任务细化到需求分析、包选择等粒度，这样能为模型提供更有引导性的思考路径。

### E.2 信息过载

在 MetaGPT 中，作者采用全局消息池和订阅机制来应对“信息过载”问题，也就是接收到过多或无关信息的问题。这个问题与具体应用场景密切相关。MetaGPT 通过消息池简化通信流程、提高效率，再通过订阅机制过滤无关上下文，提升信息的相关性和可用性。对于软件设计场景和标准操作流程而言，这种设计尤其关键，因为高效沟通本身就是协作成功的核心条件。
